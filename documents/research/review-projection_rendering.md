# 投影渲染方案审查

调查日期：2026-10-20。基线为签名检查点 `671755d`；范围为 `26.3-neoforge`，其他 Target 不变。以下是动手前的源码审查，运行结论另由本轮验证记录给出。

## 问题

恢复完整方块，同时解决投影面的共面竞争、渐变与透明物的交叠、单面出口裁切的缝隙和空洞。传播问题仅审查；跨维度与远距离另见本轮可行性报告。

## 方法

检查捕获、合成、模型、物理形状、出口坐标与拓扑；对照本机实际 26.3 NeoForge 字节码确认原版固体和透明绘制顺序。运行验证使用独立世界、固定相机和 Vulkan，不以历史测试通过推断画面正确。

## 发现

### 当前链路

`GlassChannelCaptureContext` 为每个投影网络持有独立世界渲染器、提取器、颜色和深度目标。相机由投影仪中心变换到终端出口；仅接受客户端同维度已加载区块。捕获后恢复主相机和 GPU 状态。多个网络会重复编译同一世界的区块网格，增加 CPU、显存和离屏目标占用，本轮不测量性能。

`GlassProjectionCompositor` 当前在整个 `LevelRenderer.render` 返回后合成，使用 `TRANSLUCENT` 混合并写深度；顶点 alpha 控制关闭动画。因此问题不仅是传统排序：前方透明物已经画完，后置投影还可能覆盖它。26.3 的 OIT 不能替后加的通道修正遮挡。

`GlassSurfaceGeometry` 的面在方块边界；相机出口基准则是终端朝外相邻格的中心。`GlassExitPlane` 从该中心沿法向回退 `0.5 - 1/1024`，实际进入保留区 `1/1024` 方块。这个偏移可能裁掉紧贴边界的正面；改变它也可能留下前一层侧边，必须成对验证。

### 按可见影响排序

| 问题 | 根因 | 建议修法 |
| --- | --- | --- |
| 完整方块与画面闪烁 | 原模型面与投影四边形同处整格边界 | 由每帧方块渲染器统一分配面：投影接管的面从原模型提交中移除，只提交一份完整面 |
| 水、玻璃、云交叠错误 | alpha 混合且合成晚于透明绘制 | 在原版固体 pass 末尾提交不透明投影、写深度，先于经典透明和 OIT；渐变在 shader 内混合原外观与频道画面 |
| 裁切面贴面消失或边缘露缝 | 出口基准相差半格，余量推进保留区 | 显式区分相机出口中心和整格边界，以紧贴及一纹素间距两个固定用例确定唯一余量 |
| 连通面上多频道重叠（R02） | 各投影仪分别求解并提交，没有面所有权仲裁 | 服务端按稳定优先级统一分配 `(维度, 位置, 面)`；需要另定先占者持久性，本轮不改 |
| 连接外观与传播含义不一致（R05） | `WIRED/SUPPORT` 状态与求解器按 GLASS 方块及外露面判断并非同一合同 | 先决定传播按物理共边还是显式连接，再统一输入和玩家说明，本轮不改 |
| 远端区块或维度不可见 | 捕获复用唯一 `ClientLevel`，没有远端数据订阅或第二世界 | 需要独立视图的数据与生命周期设计；仅服务端加载区块不足以解决 |

最可能导致原型失败的三处是：面移交与异步区块编译不同步；合成插入时仍处于活动 GPU pass；裁切保留侧与边界余量方向错误。验证分别覆盖动态开关、透明物前后交叠及成对边界用例。

## 结论

选择原版方块实体渲染提交来逐帧过滤模型面，使面移交不依赖异步重建区块。方块实体仅提供显示提交入口，频道和关系仍由世界级状态保存；代价是每个 GLASS 方块增加显示实体和逐帧提交。原模型改为整格立方体，物理与选中形状同步为整格。

投影批次在主世界固体 pass 开始前上传，在 `executeSolid` 返回时使用同一个活动 pass 绘制，避免嵌套 pass，并在两种透明路径之前写入深度。使用 shader 内不透明混合，不增加旧路径开关。没有选择模板缓冲：当前主深度目标为 `D32_FLOAT`，现有原生逐帧模型提交已能实现单一面所有权，无需更换目标格式。

本报告中的 R02、R05 分析对应历史移植审计，但没有宣称修复。裁切常量和最终可见结果必须以本轮固定场景为准。
