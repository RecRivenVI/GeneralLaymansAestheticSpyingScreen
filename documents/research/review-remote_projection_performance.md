# 路线 B 性能测量

调查日期：2026-10-20。1.21.1 NeoForge 的统一路线 B 已完成客户端、A/B、远端、移动 Sable、独立服务端与网络测量。最明确的成本是逐网络捕获源画面和持续源网格编译；共享订阅避免了第二观看者重复加载源，但仍增加编码工作。本轮只加验证工具与探针，产品和预算未改，未提交、未推送。

并行客户端、GPU 动态频率及四逻辑处理器限制使本轮不能给出机器峰值性能、可靠的整帧 B/A 百分比或 Sodium 加速比。第二观看者是 FakePlayer，只覆盖服务端订阅、票据与 GLASS 编码，不包含第二连接的压缩、发送和客户端工作。以下比例均注明分母；CPU、GPU、工作线程和服务端时间不能相加成一个总成本百分比。

## 问题

测量前登记的三个风险为：每个网络重复持有渲染器与帧缓冲并捕获源画面；独立世界编译及跨区块重新接收带来等待；81 个 FULL 区块与实体推进占用服务端时间。风险记录位于验证的 `task/risks.json`，先用最小配对确认可测，再扩大固定矩阵。

## 方法

入口见[验证说明](../../validations/performance-remote_projection/validation.md)。结果根目录为 `validations/performance-remote_projection/result`，输入与候选身份集中在其中的 `candidate.json`。本报告表格来自 `measurements.json` 与 `network-measurements.json`，分帧 CSV、窗口元数据和 `host.jsonl` 是本次交付的原始证据。

### 场景与采集

主机为 Intel Core i7-14700K、GeForce RTX 4080 SUPER 16 GiB，NVIDIA 驱动 617.14。Minecraft 1.21.1、NeoForge 21.1.264；Sodium 与 Sable 的固定版本见[依赖登记](../reference/dependency-runtime.md)。

- 自动客户端使用 OpenGL、1920×1080、静音、Fancy、关闭 VSync、帧率上限 260；进程限制四逻辑处理器、BelowNormal，防止多线程测试挤占用户工作。这是受限自动实例的测量。
- 四块 3×3 屏幕固定在同一视角，各为独立投影网络，选择同一终端。源包含色墙、玻璃柱和 32 只猪。A、B 从同一份关闭后的世界副本启动；猪的 AI、天气计时与随机相位没有冻结。矩阵中没有 Sable、CSL 或 Zume。
- 每窗预热 12 秒、采集约 15 秒。顺序为 A：0/1/2/4，B：0/1/2/4/4/2/1/0，A：4/2/1/0；每个网络数构成 A/B/B/A。随后 B 加 Sodium 按同样的双向网络数顺序采集。
- 帧时间取 `Minecraft.runTick` 相邻开始的间隔，每窗丢弃携带前一段等待的首行。捕获与绘制分别包围 `capture`、`drawProjector`，记录墙钟和渲染线程 CPU 时间。Windows 线程 CPU 时间较粗，采用整窗均值，不以单帧零值解释为无成本。
- GPU 使用异步时间戳环，不调用 `glFinish`。总跨度包围 `GameRenderer.render`，阶段跨度包围对应 GLASS 调用。时间戳跨度可能包括提交空隙、调度和抢占，不能当作独占 GPU busy；不含 Present 等待。缺失查询以负值排除。
- 原版 `SectionCompiler` 与 Sodium meshing worker 分别计数并累计工作线程墙钟，按实际主世界或源世界分类。它不是独占 CPU 时间。独立世界数量、区块数、上下文与帧缓冲数另由项目探针读取。
- 每约两秒采样全部 Java 进程的 PID、窗口标题、CPU 累计量、工作集、私有内存，以及 WDDM 分进程 GPU 引擎与显存、设备 busy、频率和功耗。采样器本身也有成本。堆使用量是窗口末端的 GC 敏感快照；WDDM DedicatedUsage 是进程分配统计，不是某个对象的精确驻留量。

### 校准与排除

最小样本中重复的一网络捕获可测，GPU 环未丢槽。开关 GPU 查询的短窗受背景负载影响，无法确定精确探针开销。早期 pilot 的总 GPU 跨度误含帧尾等待，已修正后才跑完整矩阵；该 pilot 总跨度不参与结论。第一次启动的 Mixin 包隔离错误保留为失败证据。

初次服务端样本的实体观察器持有卸载前的旧引用，不能证明实体推进；最终样本改为按 UUID 查询当前实体。最终 32 只猪关闭 AI，以稳定存活和加载状态，仍实际推进实体 tick。因此这是实体基础推进成本，不是 32 只完整 AI 的成本。

静态换位早期颜色条件把天空误认成新画面，下界的环境染色也使替换图像难以稳定分类。人工看图后作废这些视觉延迟，保留失败截图；补采窗口改用源集合与快照就绪事件计时。远端最终深蓝截图确认了换位，下界保留已查看的稳定截图，但不宣称精确的首次替换画面时间。其他固定矩阵数据没有重跑。

## 发现

### 成本排序与方向

| 顺序与分母 | 测量结果 | 可信度与归因 | 后续方向，仅建议 |
| --- | --- | --- | --- |
| 1：GLASS 捕获加绘制的墙钟 | B 无 Sodium 四网络捕获占 92.4%–93.5%；渲染线程 CPU 占 88.3%–90.4%；GPU 阶段跨度占 98.2%–98.5% | 高：捕获是这些有界阶段的主要成本；绝对时间受并行负载影响 | 先调查每网络捕获次数、分辨率与更新频率的收益和画质代价 |
| 2：客户端编译工作量 | B 一网络约 28 次/秒、四网络约 102–114 次/秒，计数全部来自源世界；A 对应稳态为零 | 高：静止源也持续编译；频率随渲染上下文增加。源码提示周期光照接收可能标脏，尚未单独隔离其贡献 | 先调查未变化光照是否仍标脏；共享静态网格必须保持原有缓冲与调度所有权 |
| 3：GLASS 捕获加绘制的墙钟 | 四网络出口绘制占 6.5%–7.6%；其 GPU 阶段跨度占 1.5%–1.8% | 中高：本场景中明显小于捕获 | 暂后于捕获和编译；不要先重写出口几何 |
| 服务端另计：单观看者平均 MSPT | 增量约 0.724 ms，为单观看者总 MSPT 的 25.3%；基线占 74.7% | 中低：配对短窗、NoAI 实体与并行 CPU 负载；不能外推所有世界 | 保留共享票据，先分离源 tick、快照提取和编码的精确 CPU 归因 |
| 服务端另计：第二观看者增量 | 约 0.445 ms，占双观看者总 MSPT 的 13.5%；FULL 仍为 81 | 中低：第二名是 FakePlayer，增加订阅与编码，没有第二条 TCP 连接 | 调查共享源快照编码；再用两台真实客户端验证传输增量 |

工作线程墙钟、渲染线程 CPU 与 GPU 会重叠，不能按以上顺序相加。客户端单独的世界 tick、接收解码和所有 Java 方法的 CPU 火焰图不在本次计时边界内，未伪造其占比。

换用整帧计时作分母：B 原版两个四网络窗口中，捕获加绘制占 `runTick` 渲染线程 CPU 的 20.2% 和 20.8%，占 `GameRenderer.render` GPU 时间戳跨度的 83.4% 和 87.1%。后者仍不是 GPU 独占 busy 占比，也不意味着能同比提高整帧速度。

A 采用检查点 `35f1fc0` 的原样发行构件，B 沿用 49 号冻结的产品构件。

有差异：B 多出独立源世界、接收和持续编译，观察到的捕获均值也更高。零网络时整帧已经差 2.842 ms，说明不能把其他行的整帧差值全归因给 B，也不能从这些非平稳窗口扣一个基线就宣称净加速比。需要安静环境再做较长 ABBA。A 加 Sodium 无法比较：原样 A 构件的旧 `setupRender` 注入与 Sodium 冲突，不能为得到比较结果去修改 A。

一致：各网络选择同一个源。B 的一至四网络始终只持有一个独立源世界与 25 个传输区块，渲染上下文与帧缓冲则分别为 1、2、4。A 的上下文引用玩家主世界；其 `worlds=1` 不表示也创建了一个独立世界。

因此这组 2/4 网络结果描述同源多屏，不能直接换算成 2/4 个不同源的容量。

有差异：无 Sodium 的 A、B 工作集均约 1.3 GiB；Sodium 组约 1.9–2.0 GiB，但这是不同 JVM 生命周期，不能全部解释成 Sodium 的固定增量。堆末值随 GC 波动，无单调的网络数斜率。WDDM 显存从约 218 MiB 基线升至四网络约 415–425 MiB，A/B 近似；Sodium 约 238–245 MiB 升至 458 MiB。每增加一网络约 50 MiB 是本场景的进程分配差值，包含渲染器和缓存，不能只称为 FBO 大小。

Sable 连续以 0.8 格/秒平移，并有三轴旋转和非均匀缩放。35 秒窗口确实改变源区块集合；从新集合头到 25 块齐全为 996 ms，这段产品门禁保持旧画面。整窗最大帧间隔 41.1 ms，故约一秒的源内容停更不能写成约一秒主线程卡死。集合齐全不等于网格视觉完成，最终运动截图已人工查看。

静态源的“跨区块”由探针把终端重建到 +32 格位置，包含场景构建、重订阅与动画，和 Sable 原生连续运动分开记录。该固定样本不代表活塞逐 tick 推动终端的延迟。首次 25 块按默认初始发送速率约需六秒，未改预算；实际可见等待还包括编译与动画。

表中的换位等待只计新源集合到数据补齐：远端 5948 ms、下界最终窗 5953 ms，前一补采窗为 6040 ms；它不包含网格完成后的视觉时延。Sable 跨区块有共同源世界的连续运动证据，和静态重建源的约六秒等待不混为同一现象。

已查看的交付截图索引在候选清单中：固定四网络、远端、下界、深蓝换位和 Sable 运动前后。画面确认了源内容出现及换位，未用日志替代看图。

真实观看者稳态出站约 10.0 kB/s，未压缩 GLASS 编码约 87.8–88.3 kB/s；FakePlayer 同样触发约 88.8–89.0 kB/s 的编码量。这里的实际字节由 Netty 管道头在 Minecraft 成帧、压缩后统计，是 TCP 负载字节，含同连接其他包，不含 TCP/IP 头；不是网卡抓包。未压缩编码量与实际 TCP 字节不能混用，不能把 FakePlayer 编码量叫作第二台机器的实际带宽。

色墙、重复方块和实体快照容易压缩，约 10 kB/s 只代表这个固定场景；复杂方块实体或大量变化的源不保证同样的压缩比和速率。

## 结论

有差异：B 的独立源同步与持续编译增加了工作；同源多网络只共享源世界和订阅，仍重复捕获并持有渲染资源。优先调查捕获与未变化光照引发的编译，其次再看共享编码。保持统一路线 B，不提出近端 A、远端 B 的混合方案。

无法比较：整帧 B/A 的稳定因果百分比、Sodium 加速比、两个真实客户端的总带宽、完整 AI 压力、安静环境的长尾和机器峰值。本轮预算保持不变；建议先在安静环境冻结天气与场景动态，延长窗口复测帧时间和捕获绝对值，并增加两个真实客户端，再由用户决定优化方向和预算。
